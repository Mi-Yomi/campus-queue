# По порядку — электронная очередь на сдачу работ

Приложение для нескольких преподавателей и независимых очередей. Студенты записываются по QR-коду, а после записи могут показывать свежий QR одногруппникам. Рабочий сайт размещён на GitHub Pages, облачный API и PostgreSQL — в Supabase. Локальный режим с Express и SQLite также сохранён.

## Быстрый старт

Нужен Node.js 22.13+ (рекомендуется поддерживаемая LTS-версия, например Node 24) и npm.

```powershell
npm ci
npm run setup
npm run dev
```

Команды выполняются в папке проекта. `setup` создаёт `.env`, локальную базу сервер создаёт при запуске. Случайный пароль администратора находится в `.local-access.txt`. Повторный `setup` существующие настройки и пароль не меняет.

- Студент / мои талоны: <http://localhost:5173/#/>
- Преподаватель: <http://localhost:5173/#/admin>
- Табло открывается ссылкой из панели выбранной очереди (с ограниченной сессией показа).
- Проверка API: <http://localhost:3001/api/health>

Остановить оба процесса: Ctrl+C в терминале запуска. При занятом порте приложение завершается, а не выбирает другой адрес незаметно.

Для запуска готовой сборки одним сервером:

```powershell
npm run build
npm start
```

После этого сайт доступен на <http://localhost:3001/>. Исходники, пароль и база не входят в `dist/`.

## Владелец и преподаватели

Вход владельца: логин `admin`, прежний локальный пароль из `.local-access.txt` остаётся действующим. Первое создание базы берёт хеш из `ADMIN_PASSWORD_HASH`; после создания аккаунта пароль хранится в таблице `users`, изменение `.env` не заменяет существующий пароль.

В разделе **Преподаватели** владелец создаёт логин и получает случайный пароль, который показывается один раз. Можно отключить/включить аккаунт и создать новый пароль. Смена пароля отзывает сессии; отключение также останавливает выдачу QR и новые записи в очереди преподавателя, сохраняя талоны.

Преподаватель создаёт отдельные очереди для своих занятий. У каждой — собственные студенты, номера, текущий вызов и настройки. Несколько преподавателей могут одновременно вызывать своих студентов; один студент может иметь по одному талону в нескольких разных очередях. Сброс одной очереди не затрагивает остальные.

## QR на 20 секунд и сохранение талона

1. Преподаватель показывает QR из панели или табло. Уже записавшийся студент нажимает **Показать QR одногруппнику** в своём талоне.
2. Сервер подписывает приглашение для конкретной очереди и поколения пары. Каждый код действует 20 секунд с момента выдачи по серверным часам. Просроченный код отклоняется, а публичная страница не выдаёт ему новую подпись.
3. Успешное открытие свежего QR даёт этому браузеру **две минуты** на ввод имени. Позиция пока не резервируется. Допуск хранится на сервере, черновик формы — в браузере.
4. Запись атомарно создаёт талон и погашает индивидуальный допуск. Двойной запрос не даёт второй талон. Одним текущим QR могут воспользоваться разные студенты.
5. Талон больше не зависит от QR: ротация, просроченная ссылка, перезагрузка страницы и перезапуск API его не отменяют. Токен браузера остаётся в localStorage, запись — в PostgreSQL (в локальном режиме — SQLite).

Кнопка **На весь экран** в панели преподавателя и на табло открывает крупный QR на белом фоне. У студента **Показать QR одногруппнику** сразу открывает такой экран. Закрыть можно кнопкой или Esc. Там, где доступен Fullscreen API, скрываются и панели браузера; иначе окно занимает всю область страницы. Ротация кода продолжает работать, а при доступном Screen Wake Lock экран не засыпает. Яркость самого устройства сайт не меняет. Скруглённый векторный QR сохраняет белое поле в четыре модуля, высокий контраст и все данные без перекрывающего логотипа.

Имя автоматически сохраняется в localStorage (`campus.student-profile.v1`) и подставляется на следующих парах, в том числе у другого преподавателя. Поле остаётся редактируемым. Старый черновик текущей очереди или имя существующего талона подхватываются автоматически. Очистка данных сайта удаляет сохранённое имя; на другое устройство или в другой браузер оно не переносится.

Свежие QR студентов доступны только с активным талоном текущей пары. Отмена, завершение и пропуск прекращают выдачу новых кодов этому студенту. Уже подтверждённая форма одногруппника продолжает работать до истечения двух минут, даже если поделившийся студент успел сдать работу. Новая пара аннулирует старые QR, допуски и активные талоны только этой очереди.

**Предел защиты:** старая фотография не позволит записаться после истечения QR. Но мгновенная пересылка свежего кода, удалённое открытие в пределах 20 секунд или помощь уже записанного человека не исключены. Сайт не доказывает физическое присутствие и не проверяет геолокацию/университетскую сеть. Для строгого допуска потребуется отдельное правило присутствия (например, управляемая сеть аудитории или подтверждение преподавателем). Двухминутное время формы начинается после успешной проверки свежего QR.

Перезагрузка сохраняет талон в том же браузере и на том же адресе сайта. Очистка данных, приватный режим после закрытия, другой браузер или переход между `localhost`, IP и будущим доменом не переносят идентификатор. При недоступном localStorage запись блокируется с объяснением. Ссылку табло с `display=` не раздавайте студентам: она позволяет показывать новые QR этой пары, но не управлять очередью; после новой пары она отзывается.

## Перенос предыдущей версии

При первом запуске v2 старая очередь переносится в `legacy`, под владельца `admin`. Номера, состояния и привязка к браузерам сохраняются. До переноса создаётся `data/queue.sqlite.pre-v2.bak`; миграция транзакционная и повторно не копирует данные. Секрет подписи, аккаунты, допуски и сессии хранятся в базе и переживают перезапуск.

## Как провести пару

1. Войти в панель преподавателя с логином и паролем. Создать очередь или выбрать существующую. В «Настройки пары» указать занятие, аудиторию и лимит очереди. Начальная аудитория 302 — пример, её можно заменить.
2. Открыть «QR-код для записи». Проверить адрес и показать код студентам либо открыть отдельное табло на проекторе.
3. Студент вводит имя. Получает номер, число людей перед ним и приблизительное ожидание. Номер восстанавливается после обновления страницы в том же браузере.
4. Нажать «Вызвать следующего». Когда работа сдана — «Завершить приём»; если студент отсутствует — «Не пришёл». После этого можно вызвать следующего.
5. «Пауза записи» запрещает новые записи и выдачу QR, но позволяет принимать уже записавшихся. Закрытие записи работает аналогично, с отдельным статусом.
6. «Начать новую пару» требует ввода `НОВАЯ ПАРА`: активные талоны отменяются, нумерация начинается заново. Старые записи остаются в базе, список в интерфейсе относится только к текущей паре.

Студент может выйти из очереди. Повторная запись после отмены или пропуска ставит его в конец. При пропуске автоматического возврата нет. Звуковой сигнал включается самим студентом и работает только при активном браузере; фоновые push-уведомления не реализованы.

## Проверка локального QR с телефона

Телефон и компьютер должны быть в одной доступной сети. `localhost` на телефоне обозначает сам телефон.

Панель предлагает адреса сетевых интерфейсов компьютера. Выберите действующий LAN IP в «QR-код для записи», например `http://192.168.1.10:5173/#/`. Виртуальные адаптеры и VPN могут показывать дополнительные адреса. Автовыбор — предположение, фактический доступ нужно проверить с телефона.

Если адрес компьютера изменился после `setup`, добавьте его origin в `ALLOWED_ORIGINS` в `.env` и перезапустите сервер. Origin содержит протокол, IP и порт, но не путь и не `#/`. Например:

```dotenv
ALLOWED_ORIGINS=http://localhost:5173,http://192.168.1.10:5173,http://localhost:3001
```

Брандмауэр Windows должен разрешать входящие соединения Node.js в доверенной частной сети. Автоматически правила брандмауэра приложение не меняет. Университетский Wi-Fi может запрещать связи между устройствами; для демонстрации подойдёт собственная точка доступа. Проверка с реального телефона в этой сессии не выполнялась.

## Устройство проекта

```text
src/                 React: студент, преподаватель, табло
public/              favicon
server/app.mjs       HTTP API, проверка данных, авторизация, CORS
server/store.mjs     SQLite и транзакции очереди
server/index.mjs     запуск HTTP-сервера
scripts/setup.mjs    создание локальных настроек и пароля
scripts/dev.mjs      запуск API и Vite вместе
tests/               интеграционные проверки API
.github/workflows/   публикация фронтенда в Pages при push в main или вручную
.env.example         описание переменных окружения
data/                локальная SQLite-база, исключена из Git
```

React + Vite создают статическую сборку. Маршруты через `#/` и относительные пути ресурсов работают на GitHub Pages в подпапке репозитория. Облачный API — Supabase Edge Function и транзакции PostgreSQL; локальный API — Express на Node.js. SQLite использует встроенный `node:sqlite` (на Node 22 он печатает предупреждение об экспериментальном API).

В облачном режиме очередь обновляется через Supabase Realtime. Публичное событие содержит только номера и состояния талонов: браузер рассчитывает своё место без дополнительного Edge-запроса на каждое событие. Панель преподавателя после события получает приватный список через авторизованный API. Полная сверка — раз в 3 минуты и при возвращении во вкладку; при недоступном Realtime — раз в 15 секунд. В скрытой вкладке опрос и получение QR приостанавливаются. Локальный режим использует опрос каждые 3 секунды. При потере связи интерфейс предупреждает об устаревших данных и блокирует действия до восстановления. Время ожидания = число людей впереди × средняя фактическая длительность завершённых приёмов этой пары, округлённое вверх до минут. Отсчёт приёма идёт от вызова до завершения. После каждого завершения среднее и оценки обновляются через Realtime. До первого измерения показывается «Пока нет данных», а первому в свободной очереди — «Вы следующий». Пропуски, отмены, нулевые/некорректные интервалы и перерывы между вызовами не учитываются. Новая пара начинает статистику заново; другие преподаватели не влияют на расчёт. Например, 7 и 5 минут дают среднее 6 минут; два человека впереди — около 12 минут. Это оценка, а не обещание.

### Данные и защита

- Состояния: `waiting`, `called`, `done`, `skipped`, `cancelled`.
- В каждой очереди транзакции SQLite и уникальные индексы гарантируют уникальные номера, один активный талон на токен и одного вызванного студента. Повтор запроса записи возвращает существующий активный талон.
- Случайный токен студента хранится в localStorage; база хранит его SHA-256-хеш. QR-приглашения подписываются HMAC-SHA256, срок проверяется сервером. Если браузер запрещает сохранение токена, запись блокируется с объяснением.
- Это идентификация браузера, **не студенческий SSO**. Другой браузер или очистка данных позволяют записаться повторно. Для публичной эксплуатации при необходимости добавить университетский вход или выдачу одноразовых кодов.
- Публичное API возвращает чужие номера без имён, групп и идентификаторов. Собственный талон доступен по токену. Имя и группа доступны администратору.
- Начальный хеш пароля владельца задан в `.env`; хеши существующих аккаунтов хранятся в SQLite (scrypt с солью). Случайная админская сессия действует 12 часов, хранится в sessionStorage, сервер хранит хеш токена. Выход отзывает сессию.
- API ограничивает попытки входа и частоту запросов; лимиты регистрации учитывают общую сеть. Лимитер находится в памяти одного процесса.
- CORS разрешает только указанные origins. Это не замена авторизации: сервер отдельно проверяет токены на каждом приватном действии.
- Vite запрещает выдачу `.env`, `.local-access.txt`, базы, исходников сервера и служебных каталогов. Production-сервер выдаёт только `dist/`.
- Локальная демонстрация работает по HTTP; перед передачей настоящих паролей и персональных данных через интернет нужны HTTPS и проверенные origins.
- Данные старых пар сохраняются без автоматического удаления. Перед реальной эксплуатацией нужно согласовать срок хранения и добавить очистку/архивирование. Резервную копию SQLite делайте при остановленном сервере, копируя каталог `data/` целиком, включая WAL/SHM при их наличии.

Не публикуйте `.env`, `.local-access.txt`, `data/`, журналы с личными данными и `node_modules/`. Они исключены из Git и из подготовленного архива исходников.

## API v2

Все изменяющие очередь административные методы ограничены `queueId` и владельцем очереди. Владелец системы может управлять всеми очередями; преподаватель — только своими.

| Метод                                                | Назначение                                                                        |
| ---------------------------------------------------- | --------------------------------------------------------------------------------- |
| `GET /api/me/tickets`                                | Талоны текущего браузера, `X-Visitor-Token`                                       |
| `GET /api/queues/:queueId`                           | Состояние очереди, собственный талон и незавершённый допуск                       |
| `POST /api/queues/:queueId/redeem`                   | Проверка `{invite}` из свежего QR; выдаёт допуск на 2 минуты                      |
| `POST /api/queues/:queueId/join`                     | `{name, grantId}`; одна активная запись на браузер в каждой очереди |
| `POST /api/queues/:queueId/leave`                    | Отмена своего талона                                                              |
| `GET /api/queues/:queueId/invite`                    | Свежий QR для студента с активным талоном этой пары                               |
| `POST /api/admin/login`                              | `{username, password}` → сессия                                                   |
| `GET /api/admin/me`                                  | Текущий аккаунт и роль                                                            |
| `GET, POST /api/admin/queues`                        | Список доступных очередей / создание своей                                        |
| `GET /api/admin/queues/:queueId`                     | Приватный список студентов                                                        |
| `PATCH /api/admin/queues/:queueId/settings`          | Настройки только этой очереди                                                     |
| `POST /api/admin/queues/:queueId/next`               | Вызвать следующего                                                                |
| `POST /api/admin/queues/:queueId/tickets/:id/finish` | Завершить или пропустить                                                          |
| `POST /api/admin/queues/:queueId/reset`              | Новая пара: `{confirmation: "НОВАЯ ПАРА", generation}`                            |
| `GET /api/admin/queues/:queueId/invite`              | QR преподавателя                                                                  |
| `POST /api/admin/queues/:queueId/display-session`    | Ограниченный доступ для табло                                                     |
| `GET /api/display/queues/:queueId/invite`            | QR табло, `X-Display-Token`                                                       |
| `GET, POST /api/admin/teachers`                      | Список / создание преподавателя, только владелец                                  |
| `PATCH /api/admin/teachers/:id`                      | `{active}` или `{resetPassword: true}`, только владелец                           |
| `POST /api/admin/logout`                             | Отзыв сессии                                                                      |
| `GET /api/admin/network`                             | LAN-адреса для локальной проверки                                                 |
| `GET /api/health`                                    | Проверка API                                                                      |

Все `/api/admin/*`, кроме login, требуют сессию: `X-Queue-Session: <token>` в Supabase или `Authorization: Bearer <token>` в локальном API. Старый `POST /api/join` закрыт, обход QR через него невозможен. Старый `GET /api/queue` оставлен только для чтения перенесённой очереди.

## GitHub Pages + Supabase

- Сайт: [mi-yomi.github.io/campus-queue](https://mi-yomi.github.io/campus-queue/).
- Панель: [вход преподавателя](https://mi-yomi.github.io/campus-queue/#/admin).
- Исходники: [Mi-Yomi/campus-queue](https://github.com/Mi-Yomi/campus-queue).
- API: `https://yyngfnqgdwayqgjrwzgl.supabase.co/functions/v1/queue-api/api`.

В текущий облачный проект перенесены владелец `admin` с прежним паролем и пустая начальная очередь. Локальная и облачная базы независимы. Локальные талоны автоматически между ними не синхронизируются.

Все облачные QR закреплены за каталогом `/campus-queue/`; старый сохранённый адрес не может отправить студента на главную страницу другого проекта. Кинотеатр на `/` имеет отдельный репозиторий. В его service worker добавлено исключение для `/campus-queue/`, чтобы офлайн-страница кинотеатра не подменяла очередь. Это разные сайты по путям одного origin, не разные домены. Браузеру с прежним worker может понадобиться обновление страницы с сетью и повторное открытие очереди.

Workflow `.github/workflows/pages.yml` запускает тесты, собирает и публикует `dist/` при push в `main`. В Variables репозитория заданы `VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY`. Это публичные параметры для браузера. **Service-role ключ и пароли в GitHub/VITE не передаются.** Если ни Supabase, ни `VITE_API_URL` не настроены, публикуется стартовая страница. Изменение Variables требует нового запуска workflow.

### Облачный сервер

`supabase/migrations/` содержит схему, ограничения и серверные операции. `supabase/functions/queue-api/` содержит Edge Function. Применять изменения схемы нужно миграциями; новые файлы создавать командой `npx supabase migration new <name>`. Функция разворачивается как `queue-api`. Встроенные серверные переменные `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` доступны внутри Supabase.

- Приватные данные находятся в `campus_private`; RLS включён, browser-ролям не даны права на схему, таблицы или серверные RPC.
- `public.campus_queue_live` доступна браузерам только для чтения. Содержит название пары, имя преподавателя, номера/состояния талонов, но не имена и группы студентов, идентификаторы их браузеров или сессии.
- SQL-функции работают с `SECURITY INVOKER`; выполнять серверные RPC может только `service_role`. Владение очередью, роль, состояние аккаунта и срок сессии проверяются в каждой приватной операции.
- Используется собственный вход по логину и паролю (scrypt), не Supabase Auth. JWT-проверка платформы для Edge Function выключена, поскольку функция проверяет собственные сессии, а студенты используют случайный токен браузера.
- Запись/вызов/сброс блокируют строку конкретной очереди в транзакции. Номера, активные талоны и текущий вызов защищены уникальными индексами.
- QR подписывается на сервере; его обновление не создаёт запись в базе. Сохраняются индивидуальный допуск, талон и изменения очереди.
- CORS разрешает текущий origin GitHub Pages и локальный порт 5173. При смене домена нужно обновить `allowedOrigins` в Edge Function и развернуть её заново.

Для нового проекта сначала примените миграции, затем создайте владельца с новым scrypt-хешем через защищённый административный доступ к базе. Хеш/пароль конкретного владельца намеренно отсутствуют в миграциях и репозитории. Раздел «Преподаватели» создаёт остальных пользователей. Секрет подписи QR миграция генерирует внутри базы.

Для локальной проверки облачного режима задайте `VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY` в игнорируемом `.env.local`, затем запустите `npm run dev:client`. Без них `npm run dev` продолжает работать с SQLite.

### Эксплуатация бесплатного проекта

Realtime уменьшает число Edge-вызовов, но не отменяет лимиты проекта: учитываются соединения, события, вызовы функций, объём базы и трафик. Один открытый QR делает около 3 Edge-запросов в минуту; скрытый QR запросов не делает. Проверены 20 одновременных записей, это функциональная проверка, не измерение максимальной нагрузки. Следить за реальным использованием нужно в Supabase Usage.

История пар сохраняется; автоматического удаления старых талонов пока нет. Перед длительной эксплуатацией задайте срок хранения и резервное копирование PostgreSQL. Advisor сообщает информационное `RLS Enabled No Policy` для закрытой схемы: отсутствие политик намеренно запрещает доступ обычным ролям ([описание Supabase](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy)). Сообщения об ещё не использованных индексах на новой базе не требуют их удаления ([описание](https://supabase.com/docs/guides/database/database-linter?lint=0005_unused_index)).

## Проверки

```powershell
npm test
npm run build
```

15 интеграционных тестов локального API проверяют изоляцию преподавателей, параллельные очереди, приватность, права владельца, точную границу 20-секундного QR, подделку и чужие приглашения, двухминутный допуск, переполнение и паузу, дубли/повторы запросов, восстановление талона со старой ссылкой, отзыв аккаунтов/сессий, ограниченный доступ табло, перезапуск и миграцию v1 с сохранением талонов. Тесты используют отдельные временные базы.

Браузерная проверка: создание преподавателя и очереди, запись по QR, показ QR одногруппнику, смена кода, восстановление формы и талона после перезагрузки, мобильная ширина. Фактический доступ с реального телефона через университетский Wi-Fi нужно проверить отдельно.

Дополнительно 5 тестов проверяют обновление личного талона из обезличенного Realtime-снимка: позицию, вызов, завершение, новую пару и старые события. На настоящем Supabase проверены 20 параллельных записей, восстановление/повтор запроса, QR студента и его истечение, изоляция преподавателя, вызов и сброс, отзыв табло/аккаунта, запрет прямого доступа к серверным RPC и приватным таблицам, получение события через анонимный WebSocket. Временные тестовые записи удалены после проверки.

Поле группы исключено из формы и новых записей. Старые столбцы `studentGroup` и `avgMinutes` сохранены для совместимости без удаления истории; новые оценки не используют ручное `avgMinutes`. Старые клиенты могут передать группу, но сервер её больше не собирает.
